# AGENTS.md

Instructions for coding agents (Gemini CLI, Claude Code and others) working on this showcase.

## What this repository is

It is the public showcase of the architecture of a SaaS whose code is private. It holds only the topology, the cost guardrails, the decisions and the testing strategy, always extracted from sanitized facts. **It is not the product and must never reveal the product.**

## Main rule

**The only inputs are `facts/state.json` and `facts/decisions/`.** No claim, number, service, state or name enters the showcase unless it is in those files. When in doubt, leave it out and mention the doubt in the PR description.

## How the showcase is updated

The private project opens a `facts/*` PR with the `facts-package` label. It carries the facts, the data blocks of `README.md` and `docs/engineering.md`, and the ADRs with their index, generated by `tools/generate-readme.mjs` and `tools/generate-adrs.mjs`. Only those paths may change in a `facts/*` PR (rule R7). The automatic cycle ends at the merge of that PR: no workflow triggers an agent or opens an issue.

## On-request task: update the free text from the facts

Runs only when someone asks, on a `text/<subject>` branch. `tools/write-text.mjs` writes the text with a model when `WRITER_URL`, `WRITER_MODEL` and `WRITER_KEY` are set; without them, it exits without changing anything.

1. Read `facts/state.json`, `facts/decisions/*.md` and what changed in the facts in the last commit of `main` (`git log -1 -p -- facts/`).
2. Validate the facts: `node tools/verify-facts.mjs`. If it fails, **stop** and tell whoever asked; do not fix the facts.
3. Regenerate the data blocks of `README.md` and `docs/engineering.md`: `node tools/generate-readme.mjs`. Never hand-write what is between `<!-- generated:X:start -->` and `<!-- generated:X:end -->`. What the README front page shows comes from the `featured` field of `facts/state.json`; the complete lists go to `docs/engineering.md`.
4. Read `README.md`, `docs/engineering.md`, `docs/how-this-repo-works.md` and `docs/roadmap.md` **in full** and update the free text (outside the markers) wherever it contradicts the facts, including sentences you were not going to touch: the reviewer rejects outdated old text (criterion 8). Keep the title, the "Author" section and the tone: short sentences, no marketing, no numbers that are not in the facts.
5. Regenerate the ADRs: `node tools/generate-adrs.mjs`. Never hand-write in `docs/adr/`: CI compares the folder with `facts/decisions/`. An ADR is never deleted; a withdrawn decision becomes "Status: superseded" in the facts.
6. If a `clouds[].protections[]` entry points to a `file` in `finops/`, check that the file exists and that the description in `finops/README.md` matches it. Use `<PLACEHOLDER>` for any account value.
7. If the `roadmap` changes, update `docs/roadmap.md` only in the conditions; the original topology stays there, marked as planned.
8. Run, in this order, and open the PR only if all four pass:
   - `node tools/verify-facts.mjs`
   - `node tools/generate-readme.mjs --check`
   - `node tools/generate-adrs.mjs --check`
   - `node tools/check-leaks.mjs`
9. Open **one** PR titled `showcase: update from facts of YYYY-MM-DD` (the date is `generatedAt`). In the description, list what changed by section and what was left out, with the reason.

## Automatic review and merge

A PR from a `text/*` branch goes through the `revisao` check, in addition to `verificar` and Sonar. It has no auto-merge: a person does the merge.

- The `revisao` check combines the deterministic rules (`tools/review-text.mjs`), the SonarQube Cloud quality gate and a semantic review (`.github/reviewer/instructions.md`). Read the rules and the instructions before starting: they are the criteria for your PR. A Sonar finding is fixed in the code, never by disabling the rule.
- **If `revisao` fails**, the reason is in the "Reviewer: rejected" comment on the PR. Fix only what is listed, in the same PR, and run the verifiers of step 8 again.
- After 3 rejections, or if the reviewer itself fails, the PR gets the `needs-human` label and auto-merge is turned off. From then on, **do not change the PR**.

## Never

- Change `facts/`, `tools/`, `.github/` or this file in an update task. Those files change only through a human PR or the `facts-package` package.
- Write account identifiers (GUID, OCID, billing account, project ID), provider-generated hostnames (`*.workers.dev`, `*.azurestaticapps.net`, `*.run.app`, `*.web.app`…), public IPs, emails, user paths or keys. CI blocks them, but the branch is already public before CI runs.
- Infer or cite the business domain of the product: sector, audience, features, screens, prices or plans. The showcase is about architecture, not the product.
- Invent capacity (RPS, SLA, concurrent users) or change the state of a component (for example, `planned` to `published`).
- Copy code from any other repository. The content here is Apache 2.0.

## Environment

- Node.js 24 or later is enough; the scripts in `tools/` have no dependencies. There is no `npm install`.
- Language: English.
- Line endings: LF.

## Structure

| Path | Contents |
|---|---|
| `facts/` | Sanitized input: `state.json` (validated by `state.schema.json`) and `decisions/` |
| `docs/adr/` | ADRs and their index (`README.md`), generated from `facts/decisions/` |
| `docs/engineering.md` | Complete quality practices and engineering process (data blocks generated) |
| `docs/how-this-repo-works.md` | How the showcase is kept up to date, and the automation behind it |
| `docs/roadmap.md` | Planned backend topology and conditions to enter |
| `finops/` | Zero-cost guardrails per cloud, applicable with the CLIs |
| `tools/` | Facts validator, README and ADR generators, leak checker, free-text rules and API writer |
| `.github/workflows/` | Leak-check CI, reviewer and auto-merge |
