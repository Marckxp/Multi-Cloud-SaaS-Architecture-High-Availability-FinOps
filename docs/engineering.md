# Engineering practices and process

The front page shows a short selection. This page has the complete lists, generated from `facts/state.json`. The test suites and their counts are in the [Quality section of the README](../README.md#quality).

## Quality practices

<!-- generated:practices-all:start -->
- TDD: the test fails for the right reason before the implementation
- Compiler warnings treated as errors; XML documentation required in CI
- Security headers and CSP tested end to end
- Service worker tested end to end: returns to the app from the cache and opens offline
- Service worker hardened against a redirected response from the edge, with a simulated redirect in the end-to-end tests
- Every release checked by script the way a client would see it: headers, wasm type, environment, second visit, service worker cache and offline open
- SonarQube Cloud quality gate on pull requests
- Git pre-commit hook that scans the staged content and blocks a secret before the commit exists
- Third-party actions pinned to the full commit SHA, not to a tag
- Upgrade tested on the published beta: the app opens with the profile written by the previous version and checks that local data survives; the profile is kept only if the run is green
- The .NET SDK and workload set pinned in a version file, so beta and production publish with the same runtime
- Production published only by manual dispatch, with a typed confirmation and only commits that already passed a green beta
- Dependency updates in monthly PRs, with a 14-day wait and no major versions of the .NET packages
- Local Firebase (emulators) as the default target; the real project only when the emulator does not respond
- Per-file documentation in a mirror of the tree, with invariants and reasons rather than signatures

## Engineering process

<!-- generated:process-all:start -->
- Every delivery goes through specification, plan, TDD execution, independent review and fixes with tests
- Minor review findings are recorded with an owner and a time to resolve them
- Development assisted by specialized agents per layer (domain, data, UI, hosts, e2e, review, debugging, documentation research, cloud)
- Each agent has a model and effort level set by the type of work, and an orchestration step decides what runs in parallel and how to evaluate what comes back
- This showcase is updated from a sanitized fact package: the README data blocks and the ADRs are generated by script, and CI (facts, leaks, secrets and SonarQube Cloud) blocks any PR that fails
- Each cloud has a versioned file of free-tier quotas, checked against the official source, with an operational limit of 80%
- Cloud operations (publishing, checking resources, costs and quotas) go through an infrastructure agent called by the main session, with mandatory checks and the pitfalls already hit on record
